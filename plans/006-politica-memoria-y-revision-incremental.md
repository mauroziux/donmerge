# DonMerge · Política desde la rama destino y memoria por archivo

Plan propuesto el 19 de noviembre de 2026 sobre `main` en `d0e7efe`. Las dos prioridades de producto son que cada PR se revise con las reglas vigentes en su destino y que una corrección del equipo se aplique en los archivos para los que tiene sentido.

| Entrega | Resultado observable | Orden |
|---|---|---|
| 1. Política | Un PR a `develop` usa las reglas de ese commit de `develop`, incluso si el PR propone cambiarlas. | Primera entrega de producto. |
| 2. Memoria | El mantenedor puede ver qué regla recibió el revisor, de dónde salió y revocarla. | Segunda entrega de producto. Puede prepararse la migración mientras se valida la primera. |
| 3. Claves | Cada consumidor usa una credencial nueva de su entorno y las anteriores reciben `401`. | Iniciar el inventario de inmediato. La rotación es independiente de las dos mejoras. |
| 4. Revisión incremental | Tras reescribir el historial, el check identifica el nuevo SHA y declara el alcance que realmente se revisó. | Preparar la regresión de inmediato. Integrar con el contrato de base de la entrega 1. |

## 1. Fijar la política al commit de destino

El workflow ya captura `pr.base.sha` y `pr.head.sha`. Hoy pide `.donmerge` y sus *skills* sin pasar un `ref`. Las guías que presenta como estándares proceden del `head`. Esto permite que el revisor combine reglas de tres versiones cuando la rama predeterminada, el destino y el PR difieren. [Workflow](../src/workflows/code-review/code-review-workflow.ts) · [Carga de configuración](../src/workflows/code-review/donmerge.ts) · [Construcción del prompt](../src/workflows/code-review/prompts/builder.ts)

- Leer `.donmerge`, sus *skills* y las guías normativas que ya reconoce el proyecto (`AGENTS.md`, `CLAUDE.md`, `.cursorrules`, `CONTRIBUTING.md` y `DEVELOPMENT.md`) desde el repositorio de destino en el `baseSha` capturado. Pasar ambas referencias explícitamente por el workflow. Reservar un bloque del prompt para la política y otro para el código, el diff, el README y la configuración técnica del `head`, identificados como material del PR.
- Conservar los valores por defecto cuando el archivo opcional esté ausente en la base. Distinguir el archivo ausente, la configuración inválida y el fallo de lectura. Ante errores transitorios, reintentar. Si no puede determinarse la política, informar la causa en el check y evitar un veredicto favorable. Validar el esquema con configuraciones representativas antes de endurecer el tratamiento de campos desconocidos.
- Registrar `baseSha` y `headSha` en el resultado. Revalidar ambos tras descubrir archivos y antes de publicar. Si cambió el destino durante la revisión, descartar el resultado obsoleto y solicitar el snapshot vigente al coordinador. Incluir en la detección de cambios relevantes las guías y los *skills* que ahora podrían saltarse por ser Markdown.

**Aceptación.** Crear una prueba del workflow con reglas distinguibles en `main`, `develop` y el PR. El PR a `develop` cambia una exclusión, un *skill* y una guía. Comprobar los archivos efectivamente seleccionados, las instrucciones que llegan al modelo y sus dos SHA. Repetir con un fork, un cambio de destino, una base que avanza durante el run y un repo sin `.donmerge`. Tras integrar una regla en destino, el siguiente PR debe recibirla. [Lectura por referencia en GitHub](https://docs.github.com/en/rest/repos/contents#get-repository-content)

## 2. Dar alcance y procedencia a la memoria D1

DonMerge ya vincula respuestas a hallazgos publicados y conoce el archivo del comentario. Esa ruta se pierde al guardar el aprendizaje. El selector actual recibe únicamente organización y repositorio, y elige por categoría y confianza. [Captura de feedback](../src/workflows/code-review/feedback-handler.ts) · [Selección de memoria](../src/workflows/code-review/memory-store.ts) · [Esquema D1](../migrations/0004_create_memory_tables.sql)

1. **Persistencia y compatibilidad.** Añadir una migración D1 aditiva para alcance (`file`, `directory`, `repo`), ruta, estado, origen verificable y autor de la confirmación o revocación. Usar el PR y el identificador del comentario o reacción para deduplicar entregas. Aplicar el registro de la señal y la actualización de la regla de forma atómica. La identidad de la regla incluye repositorio, categoría y alcance. Las filas históricas conservan alcance de repositorio y procedencia histórica. Una excepción antigua que suprime hallazgos y carece de confirmación pasa a revisión antes de volver a aplicarse.
2. **Captura.** Por defecto, una corrección en un hilo pertenece al archivo acreditado por el hallazgo de GitHub. Si falta esa asociación, conservar el feedback como pendiente. Ampliar al directorio o repositorio requiere una decisión explícita del mantenedor. Para activar una regla que silencia hallazgos, verificar el permiso de mantenimiento en GitHub y registrar quién la confirmó. Una reacción sigue contando como feedback sobre el hallazgo.
3. **Selección.** Pasar al selector los archivos que realmente entran en el diff enviado al modelo, también en revisiones focalizadas e incrementales. Priorizar archivo exacto, directorio ancestro más próximo y repositorio. Desempatar por confianza e identificador estable, deduplicar texto y limitar el total por caracteres. Usar segmentos completos de ruta. Una excepción de `src/billing/` no se aplica a `src/billing-v2/`. Si falla la lectura de D1, completar la revisión con la política base.
4. **Control del mantenedor.** Añadir una consulta por PR/run que muestre las reglas inyectadas, su alcance y el enlace al feedback. Ofrecer confirmación y revocación por identificador reutilizando el flujo de comandos de GitHub. Conservar la revocación ante reentregas. Registrar por separado las reglas enviadas al modelo y las que éste cita. El campo actual `last_applied_at` también se actualiza al acumular feedback y por sí solo no demuestra uso en un review.

**Aceptación.** Con dos repositorios que tengan la misma ruta y un PR que toque dos directorios, comprobar selección, orden, límites y aislamiento. Repetir con un evento duplicado, dos escrituras concurrentes, un actor sin permisos de mantenimiento, una regla revocada y una base de datos con filas anteriores a la migración. Comparar la selección antigua y la propuesta sobre los mismos PR antes de activar un repositorio piloto. Para evaluar utilidad, contar falsos positivos repetidos y defectos conocidos que el revisor siga detectando. Desactivar la inyección de reglas si hay que revertir el piloto, respetando las revocaciones.

## 3. Rotar las claves de la Push API

La configuración versionada contiene dos valores distintos, repetidos en staging y producción. Su vigencia en los Workers desplegados queda por verificar. El ADR-001 permite expresamente almacenarlos como variables legibles. Además, la ruta de diagnóstico tiene una rama que inicia trabajo antes de autenticar. La rotación debe cubrir todos los lectores de la clave. [ADR-001](../.planning/ADR-001-secrets-vs-vars.md) · [Autenticación](../src/api/auth.ts) · [Rutas](../src/app.ts)

1. Inventariar entornos, consumidores y trabajos que todavía consultan su estado. Identificarlos por cliente y entorno sin imprimir valores. El estado del trabajo está ligado al hash de la clave que lo inició. Coordinar la finalización de esos trabajos o una ventana de corte explícita. [Estado y autenticación de trabajos](../src/api/routes.ts)
2. Emitir una credencial distinta por consumidor y entorno, compatible con el validador existente. Conservarlas en el gestor de secretos y provisionar por Worker la lista permitida como secreto cifrado con un nombre nuevo, por ejemplo `DONMERGE_PUSH_API_KEYS`. Así puede prepararse antes del cambio de código sin colisionar con la variable antigua. Usar un único validador antes de cualquier acción de diagnóstico, incluso cuando falta configuración. Limitar los modelos permitidos y pasar sus identificadores como datos a la petición.
3. Coordinar el cambio de los secretos `DONMERGE_API_KEY` de los consumidores y la versión del Worker que lee el nuevo binding. Ensayar en staging. Si hay clientes activos que necesitan solapamiento, incluir las claves salientes en el secreto solo durante una ventana con hora de cierre y responsable. Retirarlas al concluir. Eliminar los literales de ambos bloques de Wrangler, actualizar el ADR y comprobar en CI que ningún despliegue pueda reintroducirlos como `vars`. [Workflow consumidor](../.github/workflows/review.yml) · [Secretos en Cloudflare Workers](https://developers.cloudflare.com/workers/configuration/secrets/)
4. Comprobar por entorno que una clave nueva autentica una consulta propia, una retirada recibe `401` y la nueva del otro entorno también recibe `401`. Cubrir diagnóstico con pruebas locales que denieguen acceso antes de crear un sandbox. Verificar en el corte que los clientes completan creación y consulta de estado. Si falla un cliente, corregir su secreto o desplegar una versión compatible con el nuevo binding. Mantener revocadas las claves expuestas también durante la recuperación.

## 4. Probar la revisión incremental tras un force push

La fila D1 guarda el nombre de la rama destino, el último SHA revisado y la cobertura. El comparador actual acepta una respuesta satisfactoria con menos de 300 archivos y convierte `files` ausente en una lista vacía. Ejecuté esa función con respuestas simuladas. Devolvió `usable: true` para un avance lineal, una historia divergente, un retroceso y una respuesta sin `files`. Los últimos dos devolvieron cero archivos, lo que en el workflow puede producir el mensaje de que el veredicto previo sigue vigente. [Comparador](../src/workflows/code-review/github-api.ts) · [Estado incremental](../src/workflows/code-review/review-state.ts) · [Contrato de comparación de GitHub](https://docs.github.com/en/rest/commits/commits#compare-two-commits)

**Cambio propuesto.** Añadir `base_sha` a `review_state`. Una fila anterior sin ese dato obliga a una revisión completa que establece la nueva referencia. Para dos SHA distintos, heredar cobertura únicamente si la revisión previa tuvo cobertura completa, coinciden rama y SHA destino, GitHub devuelve `status = ahead`, `merge_base_commit.sha` es el SHA revisado y la lista de archivos es válida y tiene menos de 300 entradas. Si falta evidencia, usar los archivos del PR completo y registrar el motivo. Reservar el atajo «sin cambios» para una lista explícitamente vacía con ascendencia comprobada.

| Prueba | Resultado exigido |
|---|---|
| Avance lineal con cambios de código y base idéntica | Incremental desde el SHA revisado. Se incluyen los archivos del intervalo. |
| Avance lineal con lista vacía explícita y ascendencia válida | Check neutral que explica que el árbol no cambió. |
| Rebase divergente o retroceso a un ancestro | Revisión del diff completo del nuevo PR, sin herencia del veredicto anterior. |
| Falta `files`, falta la base común, ésta es distinta, hay 300 archivos o falla la API | Volver al diff del PR. Si su cobertura también resulta parcial, declararla. |
| Avanza la base, se cambia de destino, falta `base_sha` o la revisión anterior fue parcial | Revisión completa y actualización del estado solo para el snapshot vigente. |
| Llega otro push mientras se revisa | El resultado obsoleto no reemplaza el estado del nuevo SHA. |

**Ensayo de extremo a extremo.** En un PR desechable de staging, partir de dos archivos de código, obtener cobertura completa en `H1` y hacer un push lineal `H2`. Esperar el check incremental. Desde la base original, preparar una historia alternativa `H3` y sustituir la rama de prueba con `--force-with-lease`. Dejar actuar al webhook de `synchronize` y a la cola. Un disparo manual forzaría una revisión completa y ocultaría el fallo. Contrastar el manifiesto de `H3` con `git diff --name-only BASE...H3`, comprobar el SHA del check publicado, la ausencia de `incrementalSince` y la fila D1. Repetir con un retroceso. Un push lineal posterior a un `H3` completamente revisado debe volver a ser incremental.

Cerrar cada entrega de código con `npm run typecheck` y `npm run test`. Si el ensayo de ascendencia falla, usar `DONMERGE_INCREMENTAL_REVIEW=false` para que el Worker revise el diff completo mientras se corrige.
